# TimeCraft — Architecture & Design Decisions

This document explains **why** the system is built the way it is — the
decisions, the alternatives considered, and the trade-offs accepted. For
"how to run it" see the [README](README.md); for deployment see
[docs/deploy-aws.md](docs/deploy-aws.md).

## System overview

```
            ┌────────────────────────────────────────────────┐
            │  Browser (React 19 / Next.js 16 App Router)    │
            │  Zustand stores ── optimistic cache per domain │
            └───────┬───────────────────────────┬────────────┘
     HTTPS (Caddy)  │ REST /api/*               │ WebSocket
            ┌───────▼───────────────┐   ┌───────▼────────┐
            │ Next.js API routes    │   │ Pusher Channels│
            │ createHandle wrapper: │   │ project-{id}   │
            │ session→rate limit→   │◄──┤ (broadcast on  │
            │ zod→RBAC→handler      │   │  every mutate) │
            └───────┬───────────────┘   └────────────────┘
                    │ Drizzle ORM (no prepared stmts — pooler)
            ┌───────▼───────────────┐
            │ Supabase PostgreSQL   │
            └───────────────────────┘
   External: Google OAuth · Anthropic API · Google GenAI · Sentry
```

One EC2 container serves the app (stateless, disposable); state lives in
Supabase. The same codebase also deploys to Vercel unchanged.

## Ordering: fractional indexing, not integer positions

**Decision.** Every sortable row (columns, tasks) carries `orderFraction: text`
generated by the `fractional-indexing` package. Moving a card writes **one
row** — a new key lexicographically between its neighbors.

**Why not `position: integer`?** Integer positions make a move O(n): inserting
between position 4 and 5 renumbers everything after. Under concurrent editing,
two users renumbering the same column simultaneously corrupt each other's
writes. Fractional keys make every move independent — two users can insert
into the same gap and both writes survive (last-write-wins per row, no
cross-row invalidation).

**Trade-off.** Keys grow longer with repeated insertion into the same gap
(pathological case: ~1 char per insert). Accepted: real boards don't insert
thousands of times into one gap, and a background re-index is possible later
without changing the schema.

## Optimistic UI with snapshot/revert

**Decision.** Every mutating store action follows one pattern: snapshot the
affected rows → apply the change to local state immediately → call the API →
merge the server response, or restore the snapshot on failure.

**Why.** Drag-and-drop feels broken with a 200–500 ms round-trip in the
middle. Optimistic writes make every action instant, and the snapshot makes
failure recovery deterministic (no refetch storm).

**The subtle part — stale responses.** Rapid successive updates to the same
task can resolve out of order. Each update gets a monotonically increasing
request id per task (`latestUpdateReqByTask`); a response or rollback only
applies if it is still the newest request for that task. Without this, a slow
failed request could clobber a newer successful one. (Covered by unit tests.)

## Real-time: managed Pusher over self-hosted WebSockets

**Decision.** Mutations broadcast to channel `project-{projectId}`;
`useRealtimeBoard` ingests events into the same Zustand stores that optimistic
updates use — so remote changes and local changes flow through one code path.

**Why Pusher.** A self-hosted WebSocket layer needs sticky sessions or a Redis
pub/sub fan-out the moment there is more than one app instance, plus
reconnect/backoff logic. Pusher's free tier removes that entire operational
class for a portfolio-scale app. The sender excludes itself via `socket_id`
(`triggerExclusive`) so it never re-applies its own events.

**Trade-off.** Vendor dependency and a message-count ceiling. The ingest
surface is three small store actions, so swapping to Supabase Realtime or
raw WS later touches one hook, not the board.

## AuthN/AuthZ: JWT sessions + table-driven RBAC

**Auth.js v5, JWT strategy.** Sessions live in a signed cookie, not a DB
table — zero session reads per request. On sign-in the JWT is hydrated once
from the DB (organization, system role); subsequent requests skip the DB
unless the token is incomplete. A guest **Credentials provider** provisions a
shared demo account — this powers both the "Continue as guest" recruiter flow
and the E2E suite (no OAuth mocking anywhere).

**RBAC.** Permissions are a TypeScript union (`"task:create" | ...`) mapped to
roles in one file (`ROLE_PERMISSIONS`); `can()` is pure and unit-tested
(including the invariant viewer ⊆ editor ⊆ admin ⊆ owner);
`authorizeOrThrow(userId, projectIds, permission)` is the only DB-aware gate.
Routes never re-implement role logic — a new permission is one union member +
role-set entries.

## One API wrapper for every route

**Decision.** All routes go through `createHandle` / `createParamHandle`
(`src/lib/api/handle.ts`): session check → **rate limit** (sliding window,
120 req/min per user+path default, 10/min on the AI route) → Zod body
validation → RBAC → handler → structured log line (method, path, status,
duration, userId) → unified error mapping (typed `AppError`s → JSON, unknown
errors → Sentry + 500).

**Why.** Cross-cutting concerns implemented once are testable once. Adding
rate limiting and request logging later were single-file changes because
every route already flowed through the wrapper.

**Rate limiter trade-off.** In-memory sliding window, deliberately: the app
runs as one container, so shared-store accuracy (Upstash/Redis) buys nothing
yet. The limiter is one module with a documented swap point.

## AI task breakdown: streaming NDJSON with BYOK

**Pipeline.** `POST /api/ai/task-breakdown` (RBAC: `task:create`) →
provider-agnostic `streamCompletion()` (Claude `claude-opus-4-8` or Gemini
`gemini-2.5-flash`, both official SDKs) → model instructed to emit **NDJSON**,
one subtask per line → each completed line is Zod-validated server-side →
forwarded as an SSE `task` event → the client creates the card through the
normal task store, inheriting optimistic updates, RBAC, and the Pusher
broadcast.

**Why NDJSON instead of structured outputs?** Schema-enforced output
guarantees the *whole document*; consuming items mid-stream would need a
partial-JSON parser. Line-delimited JSON keeps streaming trivial (split on
`\n`) and moves the guarantee into per-line validation — a malformed line is
dropped, never forwarded.

**BYOK (bring your own key).** Provider choice and API keys are per-user
(`ai_settings`), encrypted at rest with AES-256-GCM; the API only ever
returns *whether* a key exists. Every request writes an `ai_usage_logs` row
(provider, model, input/output tokens, outcome) — cost attribution from day
one. Keys are per-user, not per-organization, so nobody unknowingly spends a
teammate's budget.

## Deployment: stateless container + managed state

**Decision.** Multi-stage Dockerfile → Next.js `standalone` output → ~200 MB
non-root runtime image with a built-in `HEALTHCHECK` against `/api/health`.
EC2 runs the container behind Caddy (2-line config, auto-HTTPS); the database
stays on Supabase.

**Why not Postgres on the instance?** A free-tier EC2 instance is ephemeral by
assumption. Keeping state in managed services means the instance can be
destroyed and rebuilt from the deploy guide in minutes — which was validated
in practice (see the "battle-tested gotchas" in the deploy guide: build OOM on
1 GB RAM, `docker restart` not reloading env files, Google OAuth rejecting
bare IPs).

**Result.** Lighthouse against the live instance: 100 desktop / 98 mobile,
CLS 0.

## Observability

- **pino** JSON logs, one line per API request, emitted from the wrapper —
  `docker logs` is immediately machine-parseable.
- **Sentry** on both runtimes, DSN-gated (no DSN → no-op), wired to the
  wrapper's 500 path and React's `global-error`.
- `/api/health` reports app + DB status for Docker HEALTHCHECK and uptime
  monitors — deliberately the only unauthenticated route.

## Testing strategy

Test the things that are *algorithmically risky* rather than chasing
coverage: fractional-indexing edge cases, optimistic rollback + stale-request
guard, the RBAC matrix and its nesting invariant, key encryption round-trips,
rate-limit window behavior (43 unit tests, Vitest). Five Playwright E2E flows
exercise the real stack — guest login, card creation, cross-column drag with
persistence verified after reload — using the guest provider instead of OAuth
mocks. CI runs lint → unit tests → build → typecheck → Docker image build on
every PR; `main` is branch-protected on the `ci` check.
